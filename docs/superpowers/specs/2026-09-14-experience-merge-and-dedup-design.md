# Объединение запросов по опыту и дедупликация по городам — дизайн

Дата: 2026-09-14
Статус: утверждён, готов к написанию плана реализации

## Задача

Два независимых улучшения бота, обсуждённые в одной сессии:

1. **Меньше запросов на один и тот же текст.** Сейчас каждый уровень
   опыта — отдельная запись в `queries` и отдельный HTTP-запрос к каждому
   источнику (`"AI (без опыта)"` и `"AI (1-3 года)"` — два прохода).
   hh и zarplata понимают несколько значений `experience` в одном запросе
   (`experience=between1And3&experience=noExperience`) — можно сократить
   число запросов и вернуть в отчёте один блок на ключевое слово вместо
   нескольких.

2. **Дедупликация вакансий-клонов.** Одна и та же вакансия (совпадающие
   компания и название, обычно удалённая работа) нередко размещается
   отдельными карточками в разных городах — у каждой свой `vacancyId`,
   поэтому существующая дедупликация по `vacancy.key` их не ловит, и
   дайджест забивается повторами одной и той же позиции.

## 1. Один запрос на несколько уровней опыта

### Конфиг

`experience` в `config.yaml` принимает либо строку (как сейчас, для
обратной совместимости), либо список:

```yaml
queries:
  - name: "AI"
    text: "AI"
    experience: [noExperience, between1And3]
```

`load_config` (`hunter/config.py`) нормализует значение поля в
`tuple[str, ...]` перед созданием `SearchQuery`:
строка → кортеж из одного элемента, список → кортеж элементов,
поле отсутствует → пустой кортеж (значение по умолчанию). Дополнительной
валидации допустимых кодов опыта не добавляется — как и сейчас для
одиночного значения, ошибка в коде опыта проявится только как пустая
выдача от hh/zarplata, а не как ошибка конфигурации.

`SearchQuery.experience` (`hunter/models.py`) меняет тип с `str | None`
на `tuple[str, ...] = ()`.

Существующие пары запросов в `config.yaml` и `config.example.yaml`
(«… (без опыта)» / «… (1-3 года)») схлопываются в один запрос на ключ:
было 8 записей в `queries`, станет 4.

### URL

`build_url` (`hunter/sources.py`) вместо одной пары `("experience", ...)`
добавляет в список параметров одну пару на каждое значение из кортежа:

```python
for exp in query.experience:
    params.append(("experience", exp))
```

`urlencode` сериализует повторяющиеся ключи корректно без `doseq` —
это уже просто список пар.

### Вакансия и отчёт

В JSON-состоянии страницы (`HH-Lux-InitialState`) у каждой карточки уже
есть поле `workExperience` со значением вида `noExperience` — тем же
кодом, что и в параметре запроса (проверено на `tests/fixtures/hh_search_sorted_with_salary.html`).

- `Vacancy` (`hunter/models.py`) получает поле `experience: str | None`.
- `parse.py`, функция `_to_vacancy`, читает `raw.get("workExperience")`.
- `digest.py` получает таблицу меток:

  ```python
  _EXPERIENCE = {
      "noExperience": "без опыта",
      "between1And3": "1–3 года",
      "between3And6": "3–6 лет",
      "moreThan6": "более 6 лет",
  }
  ```

  и добавляет метку опыта (если она распознана) в строку деталей
  вакансии, между зарплатой и городом/форматом работы:

  ```
  • Название вакансии
    Компания · 100 000–150 000 ₽ на руки · 1–3 года · Москва, удалённо
  ```

Блок отчёта остаётся один на ключевое слово; опыт указывается у каждой
вакансии индивидуально. Сортировка внутри блока — по свежести, как
сейчас, независимо от уровня опыта.

## 2. Дедупликация вакансий-клонов по городам

### Ключ дедупликации

`hunter/filters.py`, функция `dedupe`, дополняется вторым проходом:
после существующей дедупликации по `vacancy.key` (id вакансии, ловит
буквально одну и ту же карточку, попавшую в несколько групп) добавляется
дедупликация по `(vacancy.company, vacancy.name)` — глобально по всем
группам, в том же порядке обхода, что и сейчас (по группам из конфига,
внутри группы — по уже применённой сортировке по свежести). Первая
встреченная вакансия с таким ключом становится представителем, остальные
— поглощаются.

Дедупликация по компании+названию не учитывает источник (hh/zarplata) —
одна и та же вакансия, размещённая на обоих сайтах, тоже схлопывается.
Зарплата в ключ не входит: по итогам обсуждения решено не учитывать её,
это осознанный риск (в теории разные вакансии с одинаковым названием
и компанией, но разной оплатой, схлопнутся в одну — на практике внутри
`search_period` в 1 день такое маловероятно).

### Отображение города

У представителя поле `area` заменяется на объединённый список городов
всех вариантов (включая его собственный), с очисткой пустых и
повторяющихся значений:

- если уникальных городов ≤ 3 — показываются все через запятую;
- если больше — первые 3 и «и ещё N город(ов)» (склонение через уже
  существующую в `hunter/digest.py` функцию `plural`).

Если после очистки остался один уникальный город (например, вакансия
продублирована дважды в одном и том же городе), `area` не трогается.

### Возврат поглощённых вакансий и состояние

`dedupe` меняет сигнатуру: было `list[Group] -> list[Group]`, становится
`list[Group] -> tuple[list[Group], list[Vacancy]]` — второй элемент это
плоский список поглощённых вакансий (без учёта того, представитель какой
группы их поглотил).

В `run_pass` (`hunter/run.py`) поглощённые вакансии сразу помечаются
виденными через уже существующий локальный хелпер `mark_seen(vacancies,
sent=False)` (уважает `--dry-run`), сразу после вызова `dedupe`, до
проверки `store.unseen()`. Это происходит безусловно, независимо от
того, будет ли показан представитель в этом проходе или отложен
(`truncate` может перенести его на следующий раз) — иначе поглощённые
карточки продолжали бы всплывать по отдельности в следующих проходах.
Они не входят ни в счётчик новых вакансий, ни в текст дайджеста.

Если процесс будет перезапущен до следующего фактического получения
данных с сайтов (например, представитель отложен `truncate` на
следующий проход), при следующем проходе дедупликация посчитается
заново по свежей выдаче — повторная пометка уже поглощённых вакансий
идемпотентна благодаря `ON CONFLICT` в `store.mark_seen`.

## Тестирование

- `tests/test_sources.py` — `build_url` с `experience` как кортежем из
  нескольких значений даёт несколько пар `experience=` в URL.
- `tests/test_config.py` — новые тесты: `experience` строкой нормализуется
  в кортеж из одного элемента; `experience` списком — в кортеж; поле
  отсутствует — пустой кортеж.
- `tests/test_parse.py` — `workExperience` попадает в `Vacancy.experience`.
- `tests/test_digest.py` — метка опыта появляется в строке вакансии;
  неизвестный/отсутствующий код опыта не ломает форматирование; склейка
  списка городов (≤3 показываются все, >3 — первые три и «и ещё N»,
  включая проверку склонения через `plural`).
- `tests/test_filters.py` — `dedupe` схлопывает вакансии с одинаковыми
  компанией и названием из разных групп/городов, возвращает их отдельным
  списком; поглощение работает независимо от исходной группы; если
  уникальный город один — `area` не меняется.
- `tests/test_run.py` — поглощённые дедупликацией вакансии попадают в
  `mark_seen(..., sent=False)` и не учитываются в `total_new`; в
  `--dry-run` состояние по ним не пишется (как и для всех остальных
  вызовов `mark_seen` в этом режиме).

## Границы изменений

Не входит: валидация допустимых кодов `experience` в конфиге; учёт
зарплаты или формата работы в ключе дедупликации; отдельная пометка
в отчёте о том, что вакансия была продублирована (текст просто показывает
объединённый список городов, без явного «(дубликат x5)»).
