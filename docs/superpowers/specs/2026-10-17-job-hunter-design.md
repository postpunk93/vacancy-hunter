# job-hunter: весь поиск работы в одном проекте

> 17.10.2026. Объединение vacancy-hunter (код) и `~/projects/personal/job-search`
> (личное рабочее место) в один проект `job-hunter`.

## Зачем

Сейчас поиск работы разнесён по двум папкам:

- **vacancy-hunter** (git, GitHub `postpunk93/vacancy-hunter`) — код: `hunter`
  (сбор, оценка Claude, дайджест в Телеграм, xlsx) и `vacancies` (корпус
  вакансий с вердиктами для разбора рынка вместе с Claude).
- **job-search** (не в git) — личное: `profile.md`, `portrait.md`, `conflict.md`,
  `strategy.md`, `resumes/`, `letters/`, `applications.md`, `vacancies.db`.

Они уже сшиты насквозь: `hunter` читает критерии из job-search, `CLAUDE.md`
job-search подтягивает `GUIDE.md` из кода, баз две и тексты вакансий
скачиваются в обе. Владелец переключается между папками, а этап откликов
вообще живёт руками: выгрузку переносит в Google-таблицу, письма пишет сам.

Владелец хочет **последовательный поиск работы без переключения между папками**:
одна папка, в ней разговор с Claude, и Claude ведёт весь путь — от «кто я и что
ищу» до готовых черновиков отклика.

Второй смысл проекта — **портфолио** на позицию ИИ-автоматизатора / вайбкодера.
Человек, который нанимает, открывает репозиторий по ссылке из резюме и должен
понять главное: **проект закрывает весь пайплайн поиска работы с помощью ИИ**.

## Два зрителя

1. **Владелец** — пользуется каждый день, всё делает в разговоре с Claude
   в папке проекта: «собери свежие», «покажи статистику за сегодня»,
   «давай черновики по 2, 5 и 7», «слишком много копирайтеров за 60 тысяч».
2. **Посетитель GitHub** — видит чистый проект в состоянии «до первичной
   настройки»: код, инструкции для Claude, шаблоны. Ни одного личного файла.

## Цели

- Одна папка, один разговор с Claude на весь цикл.
- Пайплайн из четырёх этапов плюс постоянная донастройка (ниже).
- Одна база вместо двух.
- Воронка откликов со статусами в базе — без xlsx и Google-таблицы как
  рабочего места.
- Публичный репозиторий читается как витрина: README показывает весь путь
  и где каждый шаг в коде.
- Переезд текстовых файлов владельца (профиль, критерии, стратегия, резюме)
  без потерь и без повторного опроса. База начинается с нуля.

## Не цели

- Автоматическая отправка откликов. Финальный отсмотр документов и отклик —
  всегда руками владельца.
- Переписывание резюме под конкретную вакансию. Только выбор из готовых.
- Веб-интерфейс, дашборд, Телеграм-бот с кнопками.
- Продукт для широкой аудитории (поддержка, локализация, мастер установки
  для неподготовленных). Склонировать и пройти настройку должно быть можно,
  но полировка под чужих пользователей — не цель.

## Анти-цели (провал, даже если всё работает)

- Личное попало в git или на GitHub: профиль, резюме, письма, база, конфиг
  с запросами, `.env`.
- Агент сделал что-то перед работодателем от имени владельца без его явного
  решения.
- Переезд потерял содержимое профиля, критериев, стратегии или резюме.
- Инструкции для писем разрослись в отдельный проект. Письма — короткие
  инструкции, посмотреть на результат, при необходимости поправить.
- Репозиторий выглядит как парсер hh с обвесом, а не как ИИ-пайплайн.

## Пайплайн

### 1. Первичная настройка

Признак первого запуска — нет `me/profile.md`. Тогда Claude начинает опрос
вместо любой другой работы.

Опрос наследует цикл из нынешнего `hunter/corpus/GUIDE.md`: рассказ
о себе → примеры «нравится / похоже, но нет» (`vacancies fetch` + `mark`
со слов владельца) → портрет и команды сбора → пробный сбор и отбор →
уточнение, пока выборки не станут точными → резюме и стратегия. Правила
GUIDE сохраняются: вердикты ставит владелец, полный текст — выборками,
код выхода 3 (блокировка hh) — стоп и не повторять.

На выходе в `me/`:

| Файл | Что внутри |
|---|---|
| `profile.md` | Три раздела: **кто я** (опыт, сильные стороны, город — из нынешнего `profile.md`), **что ищу** (роли, признаки «да» и «нет» по каждой, деньги, формат — из `portrait.md`), **красные флаги** (тяжёлые и мягкие признаки конфликтности — из `conflict.md`). |
| `strategy.md` | Позиционирование, что сделать до откликов, очередь. Отдельно, потому что меняется чаще и по другой причине. |
| `config.yaml` | Поисковые запросы и настройки — строгий формат для программы. |
| `resumes/<роль>.md` | Резюме под каждую роль. |

### 2. Сбор и оценка

То, что делает `hunter` сейчас, но запускается из разговора: «собери
свежие» → проход → короткая сводка в чате с лучшими вакансиями и числом
отсеянных. Запуск `hunter` из терминала продолжает работать.

Оценка читает `me/profile.md` целиком вместо пары `portrait` + `conflict`.
Промпт оценки переписать под один файл с тремя разделами;
правило «три тяжёлых флага — ниже 5» сохраняется. Проверить на реальных
данных, что рост промпта не ухудшил оценки и не сделал проход заметно
дольше или дороже; если ухудшил — сказать владельцу, а не молча резать.

Телеграм уходит с основного пути: отправка остаётся опцией, **выключенной
по умолчанию**; без `.env` и без секции Телеграма проход работает полностью.
Фоновый запуск по расписанию (сейчас выключен: `crontab` пуст) остаётся
возможным: база одна, поэтому собранное в фоне видно в разговоре так же,
как собранное по просьбе. Перенастраивать расписание в рамках этой работы
не нужно.

xlsx — только по запросу («выгрузи в таблицу»), не после каждого прохода.

Что оценивается: только то, что приносит проход, плюс выборки из корпуса
по явной просьбе. Новый промпт проверить на вердиктах владельца из старой
`job-search/vacancies.db` (только чтение; 84 вердикта, у части есть полный
текст): оценка должна разделять его «да» и «нет» не хуже, чем нынешний
промпт на тех же вакансиях. Это разовая проверка, в новую базу старые
данные не переносятся. Результат сравнения показать владельцу.

### 3. Отклики

Процесс владельца: получил список → выбрал нужные → получил черновики
документов → если надо, сделал тестовое → отправил отклик руками.

- Выбор — словами в разговоре, по номерам из сводки или по ссылкам.
- По каждой выбранной Claude читает полный текст из базы (докачивает, если
  нет) и складывает черновики в `me/applications/<id>-<компания>/`:
  - сопроводительное письмо — обычным текстом для вставки в hh, по коротким
    инструкциям в репозитории (без образцов голоса и внешних навыков);
    опора — резюме и профиль владельца, образец удачного письма —
    `letters/<id>-<компания>.md`. Сначала короткие инструкции и посмотреть
    результат; усложнять — только по итогам;
  - какое резюме приложить и почему;
  - ответы на вопросы работодателя, если они есть в вакансии;
  - про тестовое: что просят, срок, если указан.
- Статус вакансии меняется по ходу; владелец сообщает «откликнулся»,
  «пришёл ответ», «отказ» словами.

### 4. Донастройка

В любой момент: «слишком много X», «добавь роль Y», «подними порог».
Claude правит `profile.md` или `config.yaml` и показывает, как изменилась
бы последняя выдача (по кешу, без новых запросов к hh). Так же, как в
этапе 1, вердикты к примерам — только со слов владельца.

### Статистика и напоминания

- Статистика — ответ Claude на вопрос словами («общая», «за сегодня»,
  «по ролям», «сколько откликов без ответа») по базе. Отдельного отчёта
  или дашборда нет.
- Напоминания — в начале разговора Claude коротко говорит, что висит:
  тестовое с приближающимся или прошедшим сроком, черновики без отклика,
  отклики без ответа дольше N дней. Не навязчиво: одна-две строки, если
  есть что сказать.

## Воронка

Статусы вакансии: **новая → выбрана → черновик готов → тестовое →
откликнулся → ответ** (приглашение / отказ), плюс **пропущена**
(решение владельца) и **закрыта** (вакансию сняли, hh отдаёт 403 или
«в архиве») с любого шага. У тестового — что просят и срок. Хранится в базе, история смены
статусов с датами сохраняется (нужна для «отклики без ответа N дней»
и для цифр в README).

## Одна база

Сейчас две схемы: `state.db` (hunter: `seen`, `texts`, `scores`, ключ
`hh:<id>`) и `vacancies.db` (корпус: `vacancies`, `hits`, `verdicts`, ключ —
число id). Вместо них — одна база в `me/` с общей схемой и воронкой. id
zarplata совпадают с hh (кросспостинг). Текст вакансии хранится и
скачивается один раз, кем бы ни был нужен — проходом, `vacancies fetch`
или откликом.

**Данные не переносятся** (решение владельца): новая база пустая,
вакансии собираются заново. Миграции старых баз не нужно; старые файлы
остаются на месте нетронутыми.
